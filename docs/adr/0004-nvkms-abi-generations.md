# ADR-0004: NVKMS ABI generations

- Status: accepted
- Date: 2026-10-19
- Spike: #3 (notes in `docs/spikes/sp-02-nvkms-abi/README.md`, data in `tests/abi/generations.json`)
- Refines: ADR-0001

## Context

ADR-0001 chose to drive NVKMS from Rust with sparse layouts grouped into "ABI generations" by driver version range, and to probe layouts by `paramSize`. SP-02 measured how real the problem is, over every open-gpu-kernel-modules tag from 535.43.02 to 615.78.08 (172 tags):

- The layout the backend uses falls into 10 distinct generations. It changed 9 times in 171 releases, about once every 19.
- Boundaries do not follow release series. Inside the 570 series, 570.195.03 and 570.207 differ.
- Two things vary: block sizes and field offsets (the kernel rejects a wrong size with no side effect), and the command numbers of `SET_DPY_ATTRIBUTE` and `GET_DPY_ATTRIBUTE` (21/22, then 22/23, then 21/22 again). A shifted command number is the dangerous one, because the same number can mean a different ioctl.
- Both commands are adjacent in every generation (`GET = SET + 1`), and `GET_DPY_ATTRIBUTE` exists in all 172 tags.
- Test machines: the desktop (595.99.02) is generation 8, the notebook (580.178.04) is generation 7. They differ in `no3d`, the EDID offsets and the dynamic-data size.

ADR-0001 said a layout could be tried newest-first until the kernel accepts its size. That is not enough: a size match does not prove the command numbers.

## Decision

1. **The layout table is data, generated from the headers.** `tests/abi/layout.c` is the probe, `run.sh` runs it over tags, `analyze.py --json` writes `tests/abi/generations.json`. `vivid-nvkms` embeds a table derived from that file (generated by `xtask`, not edited by hand): for each generation, its first and last known driver version and the values the backend needs (block sizes, field offsets, the `SET`/`GET` command numbers).
2. **Select the generation by exact driver version.** The running version (`/sys/module/nvidia/version`) is compared against the table ranges. Known version: use its generation.
3. **For a version newer than the table**, start from the newest generation and **validate before writing**:
   1. `ALLOC_DEVICE` with that generation's block size must succeed (the kernel checks the size) and the reply must be plausible (status, `numDisps`, handles).
   2. Read the current vibrance with `GET_DPY_ATTRIBUTE` and require a value in `-1024..=1023`. If it fails, try the other known `GET`/`SET` pair (`GET = SET + 1`).
   3. Write the same value back with `SET` and read it again; any difference aborts. Only then does the user's value go out.
   If no known layout validates, refuse to apply and say so, naming the driver version. Never guess.
4. **Verify every write** with a readback (ADR-0001 rule 6). It is also what catches a wrong command number that happens to match a size.
5. **A scheduled CI job keeps the table current** (#31): it probes the new tags, regenerates `generations.json`, and opens an issue when a tag does not fit any known generation. The table is the thing a driver release can make stale, so it is the thing CI watches.
6. **Provenance and honesty about coverage.** The table says what the headers declare. A generation is marked runtime-verified only after a real driver of that generation has been exercised. Today: generation 8 (595.99.02) only. The notebook run (generation 7) is the next.

## Consequences

- One data file and one generated table replace guesses about what NVIDIA does between releases. A new driver is either a known generation, a validated guess, or a clear refusal.
- The backend is correct for any of the 172 tags without a rebuild, as long as the header analysis is right. It was not run on all of them.
- Releases will keep arriving. One layout change per ~19 releases means the table needs an update a few times a year, and CI is what makes that cheap and visible.
- Behaviour on versions older than 535 and newer than 615 is by validation only.
- Rust stays small: a struct of integers per generation, no bindgen, no copy of NVIDIA structs.

## Not covered

Runtime behaviour on any driver other than 595.99.02; the proprietary (non-open) driver's agreement with the open headers; whether NVIDIA will change the semantics of a stable field without changing its offset.

## Alternatives considered

- **Pick the layout by `paramSize` alone** (ADR-0001's first idea). Cannot distinguish generations whose sizes match but whose command numbers or offsets differ (for example 570.195.03 and 570.207).
- **Version ranges by release series.** Wrong: the 570 series contains two generations.
- **Hard-code the layout of the newest tag and hope.** This is the behaviour that makes nvibrant break on 570.207-like updates.
- **bindgen at build time against installed headers.** Distro packages do not ship the open kernel module headers, and it reintroduces the per-driver build.
